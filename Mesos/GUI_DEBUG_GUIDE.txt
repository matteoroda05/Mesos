GUI Debug Guide for MESOS
=========================

Scopo di questo file
--------------------

Questo documento non e' un semplice elenco di modifiche.
Serve a spiegare in modo pratico come e' costruita la GUI JavaFX del client MESOS,
quali file la compongono, come scorrono i dati dal server fino alla view,
e dove intervenire quando qualcosa non va.

L'idea e' questa:
- se vedi un problema di avvio, sai quali file guardare
- se vedi un problema di layout, sai quali file guardare
- se vedi un problema di dati mancanti o errati nella board, sai quali file guardare
- se vuoi rifare una schermata, capisci quali classi toccare e quali no


1. Visione d'insieme
--------------------

Il client GUI attuale e' organizzato in 4 livelli principali:

1. Entry point JavaFX
- Avvia l'applicazione grafica e crea la finestra principale.

2. Orchestrazione schermate
- Decide se mostrare connessione, lobby, waiting room o game board.
- Questo livello vive soprattutto in MesosClientApplication.

3. Service di rete lato GUI
- Fa da wrapper asincrono sopra GameClient.
- Si occupa di connect, fetch lobby, join, subscribe, refresh snapshot, chooseOffer, chooseCard.

4. Rendering e asset
- MesosGameBoardView costruisce la schermata interna di gioco.
- MesosAssetResolver trova immagini e placeholder.
- MesosUserMessageMapper trasforma messaggi grezzi del backend in messaggi leggibili per l'utente.

In parallelo esiste un quinto blocco che non e' GUI in senso stretto ma e' fondamentale:
- il server costruisce gli snapshot
- gli snapshot sono la fonte di verita' visuale della GUI
- se nello snapshot manca un dato, la GUI non puo' inventarlo


2. Flusso completo del client GUI
---------------------------------

Flusso alto livello:

1. MesosClientLauncher.main()
- chiama Application.launch(MesosClientApplication.class, args)

2. MesosClientApplication.start()
- crea stage, scene, rootStack, appShell, busyOverlay
- applica il CSS
- mostra la schermata di connessione

3. Utente preme Connect
- MesosClientApplication.handleConnect(...)
- chiama MesosGuiService.connect(...)
- se va bene, fa fetch lobby

4. Utente crea o joina una partita
- MesosClientApplication.createAndJoinGame(...) o joinGame(...)
- chiama MesosGuiService.createAndJoinGame(...) o joinGame(...)
- il service usa GameClient esistente
- il service fa anche subscribe agli update push

5. Arriva uno snapshot
- MesosClientApplication.renderSnapshot(...)
- se started == false o status == LOGIN -> waiting room
- altrimenti -> game board

6. In partita
- MesosGameBoardView.updateSnapshot(...)
- legge GameSnapshot e ricostruisce visivamente:
  - header
  - players strip
  - top row
  - offer tiles
  - turn order
  - bottom row
  - focused player
  - ranking finale

7. Utente clicca una mossa
- MesosGameBoardView non applica regole locali
- invoca callback verso MesosClientApplication
- MesosClientApplication chiama MesosGuiService
- MesosGuiService manda la richiesta al server
- il server aggiorna il game state
- torna uno snapshot o arriva un update push


3. File principali della GUI
----------------------------

3.1 src/main/java/it/polimi/ingsw/mesos/Launcher/MesosClientLauncher.java

Ruolo:
- e' il vero entry point del client grafico

Come funziona:
- contiene solo un main molto piccolo
- chiama Application.launch(MesosClientApplication.class, args)

Perche' esiste:
- separa il launcher "semplice" dalla classe Application JavaFX

Quando guardarlo:
- se il client non parte proprio
- se vuoi cambiare il main class del client

Cosa non fare qui:
- non mettere logica di schermate
- non mettere logica di rete


3.2 src/main/java/it/polimi/ingsw/mesos/Launcher/MesosClientApplication.java

Ruolo:
- e' il cervello della GUI
- orchestra tutte le schermate
- collega GUI, service di rete e board view

Responsabilita' principali:
- creare la finestra JavaFX
- mostrare la schermata iniziale
- mostrare la lobby
- mostrare la waiting room
- mostrare la board interna
- mostrare alert e status bar
- fare operazioni asincrone con overlay "Working..."

Campi importanti:
- guiService: wrapper asincrono sopra GameClient
- assetResolver: accesso centralizzato alle immagini
- appShell: BorderPane principale della finestra
- rootStack: contiene appShell + overlay di caricamento
- connectedType / connectedHost: info della connessione corrente
- gameBoardView: istanza riusata della schermata di gioco

Metodi chiave:

- start(Stage)
  Crea stage, scena, stylesheet, status bar, overlay e carica la schermata di connessione.

- showConnectionScreen()
  Mostra la prima schermata.

- buildConnectionView()
  Costruisce la UI della connessione:
  - combo socket/rmi
  - campo host
  - bottone connect

- handleConnect(...)
  Fa connect asincrono e poi fetch lobby.

- loadLobby(...)
  Chiede il LobbySnapshot al server.

- showLobbyScreen(...) / buildLobbyView(...)
  Costruisce la schermata lobby:
  - tabella partite
  - form nickname / game name / player count
  - pulsanti create, join, refresh, disconnect

- createAndJoinGame(...)
- joinGame(...)
  Innescano l'operazione lato service.

- handleJoinFlowResult(...)
  Gestisce il GameOperationResult di join/create+join.
  Se c'e' gia' uno snapshot, chiama renderSnapshot(...).

- renderSnapshot(...)
  E' il punto di smistamento principale:
  - se partita non partita -> waiting room
  - se partita partita -> game board

- showWaitingRoom(...) / buildWaitingRoomView(...)
  Costruiscono la schermata pre-start.

- showGameScreen(...)
  Crea MesosGameBoardView se non esiste ancora, poi chiama updateSnapshot(...).

- handleRemoteUpdate(...)
  Riceve i GameViewUpdate push dal server e li inoltra al renderer.

- withBusy(...)
  Utility centrale: mostra overlay, aspetta CompletableFuture, aggiorna UI.

Punti forti:
- tutta la logica di navigazione e' centralizzata
- i task di rete non bloccano il JavaFX Application Thread

Punti fragili:
- e' una classe abbastanza grande
- connessione, lobby, waiting room e transizione alla board sono tutte qui
- se qualcosa non cambia schermata, quasi sempre il primo file da guardare e' questo

Quando guardarlo per debug:
- connect non funziona
- lobby non si aggiorna
- join non porta alla schermata corretta
- gli update push non cambiano view
- compare un alert sbagliato
- finestra troppo rigida o schermate di alto livello tagliate

Se vuoi intervenire piu' miratamente:
- problemi schermata connessione: buildConnectionView, handleConnect
- problemi schermata lobby: buildLobbyView, handleJoinFlowResult
- problemi transizione waiting room -> board: renderSnapshot
- problemi overlay/loading: withBusy, setBusy


3.3 src/main/java/it/polimi/ingsw/mesos/GUI/MesosGuiService.java

Ruolo:
- service lato GUI per il networking
- e' il ponte tra la GUI e il layer GameClient gia' esistente

Obiettivo:
- la GUI non deve parlare direttamente con SocketGameClient o RmiGameClient
- MesosGuiService incapsula:
  - threading
  - stato di sessione corrente
  - subscribe/unsubscribe

Campi importanti:
- client: implementazione concreta di GameClient
- currentGameName / currentNickname: sessione attuale
- updateHandler: callback GUI per GameViewUpdate
- ioExecutor: thread pool per lavoro di rete

Metodi chiave:

- connect(ConnectionType, host)
  Chiude un eventuale client precedente e crea il nuovo GameClient.

- fetchLobby()
  Chiede le partite aperte.

- createAndJoinGame(...)
  Fa createGame, poi joinAndSubscribeInternal(...).

- joinGame(...)
  Chiama joinAndSubscribeInternal(...).

- joinAndSubscribeInternal(...)
  Fa:
  1. joinGame
  2. salva currentGameName/currentNickname
  3. subscribe agli update push
  4. restituisce snapshot dal subscribe o fallback dal join

- refreshSnapshot()
  Chiede uno snapshot manuale.

- chooseOffer(...)
- chooseCard(...)
  Mandano azioni di gioco al server.

- disconnect()
  Chiude subscription e client.

- forwardUpdate(...)
  Inoltra i push update alla GUI.

Punti forti:
- tutta la rete e' fuori dalla view
- asincrono e abbastanza pulito

Punti fragili:
- lo stato currentGameName/currentNickname e' cruciale
- se si rompe join/subscribe, la GUI puo' sembrare bloccata anche se il server funziona

Quando guardarlo:
- connect fallisce in modo strano
- join sembra andare ma non arrivano update
- refresh snapshot fallisce
- disconnect lascia sessioni sporche

Debug pratico:
- se lobby funziona ma partita no, il sospetto e' joinAndSubscribeInternal(...)
- se gli update push non arrivano, guardare forwardUpdate e la subscribe lato GameClient


3.4 src/main/java/it/polimi/ingsw/mesos/GUI/MesosGameBoardView.java

Ruolo:
- e' la schermata interna di gioco
- e' il file piu' importante per layout, resize e rendering del tavolo

Mental model:
- questa classe non decide le regole
- legge solo GameSnapshot e lo trasforma in UI

Struttura generale:
- estende BorderPane
- al centro ha un viewport custom che scala il tavolo fisso
- dentro il viewport c'e' una "design canvas" con dimensione logica fissa
- la canvas viene scalata per cercare di entrare in finestra

Costanti importanti:
- DESIGN_WIDTH / DESIGN_HEIGHT
  Dimensione logica del tavolo.
  Se la board appare minuscola o enorme, questi valori contano molto.

- MARKET_CARD_WIDTH / HEIGHT
- OWNED_CARD_WIDTH / HEIGHT
- OFFER_TILE_WIDTH / HEIGHT
- TRACK_WIDTH / TRACK_HEIGHT
  Controllano la dimensione dei pezzi principali del tavolo.

Flusso interno:

- costruttore
  Inizializza label, pane, viewport e canvas.

- updateSnapshot(...)
  E' il metodo chiave della classe.
  Aggiorna tutti i sotto-blocchi visuali:
  - header
  - players strip
  - market rows
  - offer tiles
  - turn order
  - focused player area
  - ranking

- buildViewport()
  Costruisce il contenitore scalabile.
  Qui c'e' la logica che prova a centrare e scalare l'intera board.
  Se qualcosa e' tagliato o non si ridimensiona bene, questo e' un punto centrale.

- buildDesignCanvas()
  Costruisce il tavolo in astratto:
  - header card
  - shell centrale tabletop

- buildHeaderCard()
  Costruisce la barra alta della schermata di gioco.

- buildTabletopShell()
  Costruisce il tavolo vero:
  - riga alta
  - fascia centrale
  - riga bassa
  - pannello focused player

- buildMarketLane(...)
  Crea una corsia del mercato.

- buildCenterBand()
  Costruisce il cuore del tavolo:
  - summary card
  - offer strip
  - action / ranking panel

- rebuildPlayerStrip()
  Ricostruisce la lista orizzontale dei giocatori.

- rebuildMarketRows()
  Popola top row e bottom row da snapshot.topRow() e snapshot.bottomRow().

- rebuildOfferTiles()
  Popola le tessere offerta.

- rebuildTurnOrder()
  Popola il tracciato ordine di turno.

- rebuildFocusedPlayerArea()
  Mostra stats, character cards e building cards del giocatore selezionato.

- buildCardNode(...)
  Converte un CardSummary in nodo grafico.

- buildSurfaceArt(...)
  Disegna immagine o placeholder.
  Se l'immagine manca, cade su placeholder.

Che dati usa:
- GameSnapshot
- CardSummary
- PlayerSummary
- OfferTileSummary
- TurnOrderSpaceSummary
- MesosAssetResolver

Che dati NON calcola:
- regole
- validita' della mossa oltre al minimo informativo
- punteggi reali
- transizioni di stato

Punti forti:
- tutta la board e' in un solo posto
- click actions arrivano come callback, non c'e' rete diretta qui
- asset e placeholder sono centralizzati

Punti fragili:
- e' il file piu' facile da rompere sul piano visivo
- ogni refactor di layout qui ha effetto enorme
- la logica di scaling e' delicata
- una dipendenza JavaFX mancante qui rompe il caricamento dell'intera schermata

Sintomi tipici e dove guardare:
- board tagliata:
  buildViewport, DESIGN_WIDTH, DESIGN_HEIGHT, CSS board-viewport / tabletop-shell

- card troppo grandi o troppo piccole:
  MARKET_CARD_WIDTH, OWNED_CARD_WIDTH, OFFER_TILE_WIDTH

- board non compare:
  costruttore, buildViewport, export/open del package GUI nel module-info

- click non funzionano:
  buildCardNode, buildOfferTile, canPickCard, callback passate dal launcher

- immagini mancanti:
  buildSurfaceArt e MesosAssetResolver

- focused player non cambia:
  rebuildPlayerStrip e rebuildFocusedPlayerArea


3.5 src/main/java/it/polimi/ingsw/mesos/GUI/MesosAssetResolver.java

Ruolo:
- risolve e cache-a tutte le immagini usate dalla GUI

Perche' esiste:
- evita path sparsi dentro la view
- centralizza fallback e mapping speciali

Metodi chiave:
- resolveCard(CardSummary)
  Usa assetKey del CardSummary.

- resolveTotem(Color)
  Mapping speciale importante:
  Color.BLACK -> totem_purple.png

- resolveOfferTile(char)
  Gestisce:
  B e C -> stessa immagine
  E e F -> stessa immagine

- resolveTurnOrderTile(int)
  Sceglie il tile 2/3/4/5 giocatori.

- resolveHeroImage()
  Box art della schermata iniziale.

- resolveTribeBack(Era)
- resolveBuildingBack(Era)
  Carte retro usate nella board.

- resolveRoundEventInfo()
- resolveEndGameInfo()
  Immagini informative usate nel tavolo.

Dettaglio importante:
- imageCache e' una ConcurrentHashMap<String, Optional<Image>>
- quindi immagini gia' risolte non vengono ricaricate ogni volta

Punti fragili:
- se il path e' sbagliato, il resolver non lancia eccezione: restituisce Optional.empty()
- il risultato visibile allora e' solo il placeholder nella view

Quando guardarlo:
- immagini non caricate
- asset sbagliati
- mismatch tra enum colore e risorse
- dubbio su quale file png usa una certa carta/tessera


3.6 src/main/java/it/polimi/ingsw/mesos/GUI/MesosUserMessageMapper.java

Ruolo:
- traduce messaggi backend in messaggi GUI piu' puliti

Perche' e' utile:
- il backend manda vari messaggi in italiano o anche grezzi
- la GUI deve mostrare testi inglesi e leggibili

Metodi chiave:
- describeResult(...)
- describeUpdate(...)
- describeException(...)
- describePhase(...)

Dettaglio importante:
- translateFreeform(...) fa una traduzione euristica di stringhe
- non e' strutturata da codici in tutti i casi

Conseguenza:
- se il backend cambia una frase, questo mapper potrebbe non riconoscerla piu'
- quindi alcuni testi possono peggiorare senza che la logica di gioco sia rotta

Quando guardarlo:
- messaggi brutti, misti italiano/inglese, offensivi o poco chiari
- status phase sbagliata o poco leggibile

File da toccare se vuoi cambiare UX testuale:
- quasi sempre questo

4.1 src/main/java/module-info.java

Ruolo:
- definisce il modulo Java del progetto

Per la GUI conta perche':
- dichiara requires javafx.controls
- dichiara requires javafx.graphics
- esporta e apre i package usati dal launcher e dalla GUI

Linee chiave:
- exports it.polimi.ingsw.mesos.Launcher
- exports it.polimi.ingsw.mesos.GUI
- opens it.polimi.ingsw.mesos.Launcher to javafx.graphics
- opens it.polimi.ingsw.mesos.GUI to javafx.graphics

- se mancano export/open giusti, JavaFX puo' fallire in modi poco intuitivi
- uno dei sintomi tipici e' proprio NoClassDefFoundError o problemi strani in avvio

Quando guardarlo:
- compile ok ma runtime no
- classi GUI apparentemente presenti ma non caricabili
- errori JavaFX strani in ambiente modulare

5. Come fare debug per sintomo
------------------------------

Caso A: la schermata iniziale funziona ma lobby o waiting room sono tagliate
- guardare MesosClientApplication
- guardare buildConnectionView / buildLobbyView / buildWaitingRoomView
- guardare il CSS di:
  - screen-shell
  - screen-flow
  - form-card
  - table-card

Caso B: il join va ma non apre la board
- guardare MesosClientApplication.handleJoinFlowResult(...)
- guardare MesosClientApplication.renderSnapshot(...)
- controllare se result.snapshot() e' nullo
- controllare status e started nello snapshot
- controllare se c'e' eccezione nel costruttore di MesosGameBoardView

Caso C: la board si apre ma si vede poco o e' tagliata
- guardare MesosGameBoardView.buildViewport()
- guardare DESIGN_WIDTH / DESIGN_HEIGHT
- guardare TRACK_WIDTH e dimensioni card
- guardare CSS:
  - board-viewport
  - tabletop-shell
  - market-lane

Caso D: mancano immagini
- guardare MesosAssetResolver
- guardare assetKey nei CardSummary
- guardare CardLoader.assignPresentationAssets(...)
- verificare che le resources siano davvero nel classpath

Caso E: una carta ha l'immagine sbagliata
- guardare CardLoader.assignPresentationAssets(...)
- verificare il numbering dei file png
- ricordarsi che gli event usano volutamente un'immagine generica

Caso F: click su carta o tessera non funziona
- guardare MesosGameBoardView.buildCardNode(...)
- guardare MesosGameBoardView.buildOfferTile(...)
- guardare canPickCard(...)
- guardare status nello snapshot
- ricordarsi che la GUI non abilita click se l'informazione di base dice che l'azione non ha senso

Caso G: il server sembra partire ma la GUI non si connette
- guardare MesosServerLauncher
- controllare le porte 12345 e 1099
- controllare se sono gia' occupate
- controllare NetworkDefaults

Caso H: messaggi utente brutti o sbagliati
- guardare MesosUserMessageMapper

Caso I: compile ok ma runtime JavaFX no
- guardare module-info.java
- guardare export/open del package GUI e Launcher
- guardare plugin JavaFX nel pom.xml


6. Relazioni tra file
---------------------

Catena di avvio client:
- MesosClientLauncher
-> MesosClientApplication

Catena di rete client:
- MesosClientApplication
-> MesosGuiService
-> GameClient
-> server

Catena dati di partita:
- MesosServerCore.toSnapshot()
-> GameSnapshot / PlayerSummary / CardSummary / OfferTileSummary / TurnOrderSpaceSummary
-> MesosGuiService
-> MesosClientApplication.renderSnapshot(...)
-> MesosGameBoardView.updateSnapshot(...)

Catena immagini:
- CardLoader assegna presentation_asset_key
-> MesosServerCore lo copia in CardSummary.assetKey
-> MesosAssetResolver.resolveCard(...)
-> MesosGameBoardView.buildSurfaceArt(...)

Catena styling:
- MesosClientApplication applica mesos-gui.css alla Scene
-> tutti i nodi costruiti da MesosClientApplication e MesosGameBoardView usano style class


7. Dove NON intervenire se vuoi solo sistemare la GUI
-----------------------------------------------------

Non toccare subito:
- GameFlowController
- GameState e stati di gioco
- logica ModelController
- regole di round/event/endgame

Tocca prima:
- MesosClientApplication
- MesosGameBoardView
- MesosAssetResolver
- MesosUserMessageMapper
- CSS
- GameSnapshot / DTO solo se davvero manca un dato visuale
- MesosServerCore solo se quel dato non viene costruito lato server


8. Suggerimento pratico per futuri interventi
---------------------------------------------

Se vuoi fare interventi mirati senza rompere tutto, il metodo migliore e':

1. identifica il sintomo preciso
2. trova in questo file il caso di debug corrispondente
3. modifica un solo blocco alla volta
4. ricompila con:
   cmd /c mvnw.cmd -q -DskipTests compile
5. se il problema e' di runtime JavaFX:
   rilancia client
6. se il problema e' di dati:
   controlla prima snapshot e server core, poi la view


9. Stato attuale piu' delicato
------------------------------

I punti piu' delicati della GUI, oggi, sono questi:

- la schermata interna di gioco e il suo viewport scalabile
- la transizione waiting room -> board
- la risoluzione modulare JavaFX / module-info
- la coerenza tra assetKey, risorse png e layout delle card

Se vuoi fare debug serio e mirato, parti quasi sempre da:
- MesosClientApplication
