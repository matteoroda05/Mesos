SPIEGAZIONE COMPLETA DELLA GUI DI MESOS
======================================

Scopo del file
--------------

Questo documento spiega in modo preciso come e' costruita la GUI attuale del client MESOS,
come viene usato JavaFX, quali schermate esistono, quali classi partecipano al flusso,
cosa fa il launcher e quali parti del backend sono state adattate per supportare la GUI.

Nota importante:
- questa spiegazione e' basata sul codice attuale del progetto
- nel repository esistono anche file di debug e riassunti di modifiche piu' vecchie
- quando ci sono differenze fra quei documenti e il codice, qui considero valido il codice attuale


1. Visione generale
-------------------

La GUI attuale del client e' costruita con JavaFX puro, senza FXML.

Questo significa che:
- non esistono file `.fxml`
- non esistono controller JavaFX separati stile `MyViewController`
- tutta la gerarchia grafica viene costruita via codice Java, creando direttamente nodi come:
  - `Stage`
  - `Scene`
  - `BorderPane`
  - `StackPane`
  - `VBox`
  - `HBox`
  - `FlowPane`
  - `Label`
  - `Button`
  - `ComboBox`
  - `TableView`
  - `ImageView`
  - `Alert`

In pratica la GUI e' organizzata in questi blocchi:

1. launcher del client
- avvia JavaFX

2. applicazione principale JavaFX
- crea finestra, scena, schermate e transizioni

3. service di rete per la GUI
- esegue le operazioni di rete in asincrono

4. view della board
- rende visivamente la partita usando gli snapshot ricevuti dal server

5. resolver degli asset
- trova le immagini corrette per carte, totem, sfondo e tessere

6. mapper dei messaggi
- traduce messaggi tecnici o grezzi in testi piu' leggibili per l'utente


2. Schermate della GUI
----------------------

Le schermate effettive del client sono queste:

1. schermata di connessione
- scegli il tipo di connessione: `SOCKET` oppure `RMI`
- inserisci l'host del server
- premi `Connect`

2. schermata lobby
- mostra la lista delle partite aperte
- permette di:
  - aggiornare la lobby
  - disconnettersi
  - inserire nickname
  - inserire nome partita
  - scegliere numero giocatori
  - creare e joinare una nuova partita
  - joinare una partita esistente

3. waiting room
- appare dopo il join se la partita non e' ancora iniziata
- mostra:
  - nome partita
  - numero giocatori entrati
  - tuo nickname
  - elenco giocatori presenti
- da qui puoi fare `Refresh` oppure `Disconnect`
- se la partita parte e arriva un update dal server, la GUI passa da sola alla board

4. schermata di gioco
- e' la schermata principale della partita
- mostra:
  - nome partita
  - stato della partita
  - round
  - era
  - giocatore attivo
  - picks rimanenti
  - ordine di turno minimale
  - tessere offerta
  - riga alta del mercato
  - riga bassa del mercato
  - totem del giocatore attivo
  - pannello informativo in basso

5. classifica finale
- non e' una schermata separata
- compare dentro la schermata di gioco, nel box `rankingBox`
- viene mostrata quando la partita risulta finita o lo stato e':
  - `END_GAME`
  - `END_SCREEN`


3. Flusso completo dell'applicazione
------------------------------------

Il flusso reale e' questo:

1. `MesosClientLauncher.main(...)`
- chiama `Application.launch(MesosClientApplication.class, args)`

2. `MesosClientApplication.start(Stage)`
- salva lo `Stage`
- collega l'handler per gli update remoti
- costruisce:
  - status bar
  - `appShell`
  - overlay di caricamento
  - `rootStack`
  - `Scene`
- applica il CSS
- imposta titolo, misure minime e scene
- mostra la schermata di connessione

3. l'utente preme `Connect`
- `handleConnect(...)`
- richiama `MesosGuiService.connect(...)`
- se va bene salva:
  - `connectedType`
  - `connectedHost`
- poi carica la lobby con `loadLobby(...)`

4. lobby caricata
- `loadLobby(...)`
- chiede al service il `LobbySnapshot`
- se arriva correttamente, la GUI passa a `showLobbyScreen(...)`

5. l'utente crea o joina una partita
- `createAndJoinGame(...)` oppure `joinGame(...)`
- il service esegue:
  - create game
  - join
  - subscribe agli update push

6. arriva un `GameOperationResult` con snapshot
- `handleJoinFlowResult(...)`
- se c'e' uno snapshot e il join e' avvenuto, chiama `renderSnapshot(...)`

7. `renderSnapshot(...)`
- se `snapshot.started() == false`, mostra la waiting room
- altrimenti mostra la schermata di gioco

8. durante la partita
- il server invia `GameViewUpdate`
- `MesosGuiService` inoltra l'update
- `MesosClientApplication.handleRemoteUpdate(...)` usa `Platform.runLater(...)`
- aggiorna status bar e rerenderizza la board

9. quando il giocatore clicca una mossa
- la `MesosGameBoardView` non applica regole locali
- invoca una callback
- la callback torna a `MesosClientApplication`
- `MesosClientApplication` chiama `MesosGuiService`
- il service manda la richiesta al server
- il server risponde e poi pubblica lo snapshot aggiornato


4. Come viene usato JavaFX
--------------------------

La GUI usa JavaFX in modo classico ma interamente programmatico.

4.1 `Application`, `Stage`, `Scene`

- `MesosClientApplication` estende `javafx.application.Application`
- `start(Stage stage)` e' il punto d'ingresso grafico reale
- lo `Stage` e' la finestra principale
- la `Scene` contiene il nodo root, che qui e' `rootStack`

Configurazione iniziale:
- dimensione iniziale scena: `1480 x 900`
- titolo finestra: `MESOS`
- finestra ridimensionabile
- larghezza minima: `620`
- altezza minima: `520`

4.2 Layout principali

La GUI usa soprattutto:
- `BorderPane`
  - come shell dell'applicazione (`appShell`)
  - mette la status bar in basso e la schermata corrente al centro

- `StackPane`
  - per sovrapporre contenuto e busy overlay
  - per centrare contenitori
  - per gestire immagini e totem sovrapposti

- `VBox`
  - per layout verticali
  - usata in quasi tutte le schermate

- `HBox`
  - per righe orizzontali
  - usata per bottoni, righe giocatori, righe carte

- `FlowPane`
  - usata dove serve wrapping responsivo
  - soprattutto in lobby e waiting room

4.3 Controlli JavaFX usati

Nella GUI vengono usati:
- `ComboBox<ConnectionType>` per scegliere `SOCKET` o `RMI`
- `TextField` per host, nickname e game name
- `Spinner<Integer>` per il numero di giocatori
- `TableView<LobbyGameSummary>` per la lista delle partite aperte
- `Button` per tutte le azioni
- `Label` per testi, badge, pill e status
- `ProgressIndicator` per l'overlay di caricamento
- `Alert` per messaggi di errore o informazione
- `Tooltip` per dettagli di carte, tessere e ordine di turno
- `ImageView` per logo, sfondo, totem, carte e tessere

4.4 Threading JavaFX

JavaFX ha un thread grafico dedicato, il `JavaFX Application Thread`.

Per non bloccare la GUI:
- le chiamate di rete non vengono fatte direttamente sul thread JavaFX
- `MesosGuiService` usa `CompletableFuture`
- il lavoro di rete gira in un `ExecutorService` dedicato
- quando il risultato torna, la GUI usa `Platform.runLater(...)` per aggiornare i nodi in modo sicuro

Questo e' importante per evitare:
- freeze della finestra
- blocchi durante connect, join, refresh, scelta carta o scelta tessera

4.5 CSS JavaFX

La scena carica il foglio:
- `/it/polimi/ingsw/mesos/gui/mesos-gui.css`

Il CSS definisce:
- palette colori
- sfondo globale
- pannelli
- bottoni
- tabella lobby
- badge
- card surface
- turn order bar
- ranking
- overlay

4.6 Nessun FXML

Nel progetto attuale non si usa `javafx.fxml`.
Infatti:
- nel `pom.xml` c'e' `javafx-controls`, non `javafx-fxml`
- nel `module-info.java` ci sono `requires javafx.controls` e `requires javafx.graphics`
- non c'e' nessuna dipendenza da FXML
- non ci sono `FXMLLoader`, `@FXML`, controller FXML o file `.fxml`


5. Il launcher: cosa fa e cosa e' stato fatto
---------------------------------------------

5.1 `MesosClientLauncher`

File:
- `src/main/java/it/polimi/ingsw/mesos/Launcher/MesosClientLauncher.java`

Ruolo:
- e' l'entry point del client grafico

Fa solo questo:
- `Application.launch(MesosClientApplication.class, args);`

Quindi:
- il launcher client non contiene logica di rete
- non contiene logica di schermate
- non contiene logica di rendering
- serve solo ad avviare JavaFX correttamente

5.2 `MesosClientApplication`

File:
- `src/main/java/it/polimi/ingsw/mesos/Launcher/MesosClientApplication.java`

Ruolo:
- e' il vero "regista" della GUI

Qui sono state implementate le schermate e le transizioni:
- connection screen
- lobby
- waiting room
- game screen

In pratica nel launcher lato client e' stato fatto questo:
- passaggio dal semplice avvio a una vera app JavaFX
- costruzione di una shell applicativa con status bar
- introduzione del busy overlay
- gestione della navigazione tra schermate
- aggancio degli update push del server
- delega del rendering della partita a `MesosGameBoardView`

5.3 `MesosServerLauncherApp`

File:
- `src/main/java/it/polimi/ingsw/mesos/Launcher/MesosServerLauncherApp.java`

Ruolo:
- e' il main class del jar server

Fa solo questo:
- chiama `MesosServerLauncher.main(args)`

Quindi:
- il server non usa JavaFX
- questo launcher non costruisce finestre JavaFX
- e' solo un adapter semplice per il jar eseguibile

5.4 `SwingConsoleWindow`

File:
- `src/main/java/it/polimi/ingsw/mesos/Launcher/SwingConsoleWindow.java`

Ruolo:
- e' una utility Swing/AWT, non JavaFX

Importante:
- questa classe esiste ancora nel repository
- ma non fa parte del flusso attuale del client JavaFX
- serve come pezzo legacy o supporto separato

In altre parole:
- la GUI attuale del client e' JavaFX
- `SwingConsoleWindow` non e' la GUI principale del client attuale


6. `MesosClientApplication`: spiegazione dettagliata
----------------------------------------------------

Questa e' la classe piu' importante per capire la GUI.

6.1 Campi principali

- `guiService`
  - service asincrono sopra `GameClient`

- `assetResolver`
  - resolver centralizzato delle immagini

- `stage`
  - finestra principale

- `appShell`
  - `BorderPane` principale

- `rootStack`
  - contiene `appShell` piu' `busyOverlay`

- `busyOverlay`
  - overlay mostrato durante operazioni asincrone

- `statusBarLabel`
  - testo della status bar in basso

- `connectedType`
  - `SOCKET` o `RMI`

- `connectedHost`
  - host attualmente usato

- `gameBoardView`
  - istanza riusata della schermata di gioco

6.2 `start(Stage stage)`

Fa:
- salva `stage`
- collega `guiService.setUpdateHandler(this::handleRemoteUpdate)`
- costruisce status bar
- costruisce `appShell`
- costruisce `busyOverlay`
- crea `rootStack = new StackPane(appShell, busyOverlay)`
- crea la `Scene`
- applica il CSS
- imposta titolo e dimensioni minime
- mostra la connection screen
- chiama `stage.show()`

6.3 Status bar

Metodi:
- `buildStatusBar()`
- `updateStatus(String message)`

Funzione:
- mostra in basso lo stato corrente dell'applicazione
- ad esempio:
  - connessione in corso
  - lobby caricata
  - disconnessione
  - messaggi derivati dal server

6.4 Busy overlay

Metodi:
- `buildBusyOverlay()`
- `setBusy(boolean busy, String text)`
- `withBusy(...)`

Funzione:
- durante operazioni lente la GUI mostra un overlay con:
  - `ProgressIndicator`
  - label di testo

Meccanismo:
- `withBusy(...)` attiva l'overlay
- attende una `CompletableFuture`
- al termine lo disattiva
- se c'e' un errore mostra `Alert`

Perche' e' utile:
- evita che l'utente pensi che la GUI si sia bloccata
- tiene il thread grafico libero

6.5 Schermata di connessione

Metodi:
- `showConnectionScreen()`
- `buildConnectionView()`
- `buildConnectionLogo()`
- `handleConnect(...)`

Come funziona:
- `buildConnectionView()` crea:
  - `ComboBox<ConnectionType>`
  - `TextField hostField`
  - `Button connectButton`

Dettagli:
- la connessione predefinita e' `SOCKET`
- il campo host parte da `NetworkDefaults.DEFAULT_RMI_HOST`, cioe' `127.0.0.1`
- il pulsante `Connect` chiama `handleConnect(...)`

Validazioni:
- se manca il tipo di connessione -> alert
- se l'host e' vuoto -> alert

Se tutto va bene:
- parte il connect asincrono
- poi viene caricata la lobby

6.6 Lobby

Metodi:
- `loadLobby(...)`
- `showLobbyScreen(...)`
- `buildLobbyView(...)`
- `validateLobbyActionFields(...)`
- `resolveSelectedGameName(...)`
- `createAndJoinGame(...)`
- `joinGame(...)`
- `handleJoinFlowResult(...)`

Componenti principali della lobby:
- `TableView<LobbyGameSummary>` con colonne:
  - `Game`
  - `Players`
  - `Open Seats`
- campo nickname
- campo game name
- spinner player count
- bottoni:
  - `Refresh`
  - `Disconnect`
  - `Join Game`
  - `Create and Join`

Comportamento importante:
- se selezioni una riga della tabella, il `gameNameField` viene riempito con il nome partita scelto
- `Join Game` usa il nome nel campo oppure quello selezionato in tabella

6.7 Waiting room

Metodi:
- `showWaitingRoom(...)`
- `buildWaitingRoomView(...)`
- `waitingPlayerRow(...)`

Funzione:
- rappresenta la fase in cui la partita esiste ma non e' ancora iniziata

Mostra:
- riepilogo match
- numero giocatori entrati
- tuo nickname
- lista dei giocatori entrati

Bottoni:
- `Refresh`
- `Disconnect`

Nota:
- la transizione a partita avviata non richiede un cambio manuale di pagina se il server manda un update push

6.8 Schermata di gioco

Metodi:
- `showGameScreen(...)`
- `chooseOffer(...)`
- `chooseCard(...)`
- `refreshCurrentSnapshot()`
- `handleMutatingGameActionResult(...)`
- `handleSnapshotResult(...)`

Dettaglio chiave:
- `MesosClientApplication` non disegna la board direttamente
- crea `MesosGameBoardView` solo la prima volta
- poi la riusa e le passa ogni nuovo snapshot con `updateSnapshot(...)`

Callback date alla board:
- refresh
- disconnect
- choose offer
- choose card

Quindi la board:
- non conosce il networking
- non conosce `GameClient`
- non fa richieste di rete da sola

6.9 Gestione update push

Metodo:
- `handleRemoteUpdate(GameViewUpdate update)`

Fa:
- `Platform.runLater(...)`
- traduce il messaggio via `MesosUserMessageMapper`
- aggiorna la status bar
- rerenderizza la schermata tramite `renderSnapshot(...)`

Questo e' il punto che rende la GUI realmente "live".

6.10 Disconnessione

Metodo:
- `disconnectToConnectionScreen()`

Fa:
- chiama `guiService.disconnect()`
- azzera:
  - `connectedType`
  - `connectedHost`
  - `gameBoardView`
- torna alla schermata di connessione

6.11 Helper di composizione grafica

Metodi helper usati per costruire la UI:
- `buildField(...)`
- `titleBlock(...)`
- `sectionHeader(...)`
- `helperText(...)`
- `buildActionRow(...)`
- `buildButtonStack(...)`
- `buildMetaWrap(...)`
- `metaBadge(...)`
- `centeredContent(...)`
- `buildColorChip(...)`
- `toRgb(...)`
- `showAlert(...)`

Questi metodi:
- non cambiano il flusso dell'app
- servono a centralizzare pattern grafici ripetuti

6.12 Metodi presenti ma oggi non usati

Nel codice attuale ci sono alcuni metodi privati che risultano non richiamati:
- `buildHeroCard()`
- `centeredScroll(...)`
- `centeredFixedContent(...)`

Interpretazione:
- sono resti di iterazioni precedenti o di refactoring incompleto
- non fanno danni, ma oggi non partecipano al flusso reale


7. `MesosGameBoardView`: spiegazione dettagliata
------------------------------------------------

Questa classe e' la view della partita vera e propria.

File:
- `src/main/java/it/polimi/ingsw/mesos/gui/MesosGameBoardView.java`

7.1 Ruolo

Ruolo reale:
- leggere un `GameSnapshot`
- trasformarlo in nodi JavaFX
- permettere i click solo quando ha senso farlo dal punto di vista informativo

Ruolo che NON ha:
- non applica regole di gioco
- non valida il turno in modo autorevole
- non modifica il model locale
- non contatta direttamente il server

7.2 Struttura generale

La classe:
- estende `BorderPane`
- contiene una viewport scalabile con sfondo
- dentro la viewport c'e' una canvas logica di dimensione fissa

Costanti principali:
- `DESIGN_WIDTH = 920`
- `DESIGN_HEIGHT = 370`
- `MARKET_CARD_WIDTH = 85`
- `MARKET_CARD_HEIGHT = 130`
- `OFFER_TILE_WIDTH = 85`
- `OFFER_TILE_HEIGHT = 130`
- `PREVIEW_CARD_WIDTH = 76`
- `PREVIEW_CARD_HEIGHT = 116`
- `TRACK_WIDTH = 232`
- `TRACK_HEIGHT = 204`

La board e' progettata con queste dimensioni logiche e poi scalata per stare nella finestra.

7.3 Dati e callback ricevuti

Il costruttore riceve:
- `localNickname`
- `MesosAssetResolver`
- callback `onRefresh`
- callback `onDisconnect`
- callback `onChooseOffer`
- callback `onChooseCard`

Questo e' molto importante architetturalmente:
- la board non dipende dal layer rete
- riceve solo dati e callback

Nota pratica:
- nel layout attuale `onChooseOffer` e `onChooseCard` vengono effettivamente usate
- invece `onRefresh` e `onDisconnect` sono ancora passate al costruttore ma oggi non sono collegate a pulsanti visibili dentro la board

7.4 `updateSnapshot(...)`

E' il metodo chiave.

Quando arriva un nuovo snapshot:
- salva `this.snapshot`
- aggiorna testi e badge
- aggiorna il titolo
- aggiorna il sottotitolo
- aggiorna informazioni di round/era/fase/giocatore attivo/picks
- aggiorna messaggio azione
- richiama i metodi di rebuild:
  - `rebuildMarketRows()`
  - `rebuildOfferTiles()`
  - `rebuildTurnOrder()`
  - `rebuildRanking()`
  - `rebuildMinimalTurnBar()`
  - `rebuildTotemWrapper()`

7.5 Layout della board

La board attuale e' sostanzialmente divisa in:

1. viewport con sfondo
- `buildViewport()`
- usa l'immagine `sfondo1.png`

2. tavolo centrale
- `buildTabletopCanvas()`
- `buildTabletopShell()`

3. riga alta
- `buildTopTableRow()`
- contiene `topRowPane`

4. fascia centrale
- `buildCenterBand()`
- contiene:
  - `minimalTurnBarPane`
  - `offerTilesPane`
  - `rankingBox`

5. riga bassa
- `buildBottomTableRow()`
- contiene `bottomRowPane`

6. barra informativa inferiore
- costruita in `buildTabletopShell()`
- contiene:
  - `totemWrapper`
  - `buildCompactInfoPanel()`

7.6 Viewport e scaling

Metodi:
- `buildViewport()`
- `updateBoardScale(...)`
- `buildLayout()`

Come funziona:
- la canvas viene inserita in un `Group`
- alla canvas viene applicato un `Scale`
- la viewport ascolta cambi di larghezza/altezza
- quando cambia spazio disponibile, `updateBoardScale(...)` ricalcola il fattore di scala

Formula concettuale:
- calcola spazio disponibile
- calcola dimensioni del contenuto
- usa `Math.min(availableWidth / contentWidth, availableHeight / contentHeight)`

Obiettivo:
- far stare tutta la board in finestra
- evitare scroll nella schermata di gioco

7.7 Riga alta e riga bassa del mercato

Metodi:
- `rebuildMarketRows()`
- `renderSnapshotRow(...)`

Come funziona:
- la riga alta usa `snapshot.topRow()`
- la riga bassa usa `snapshot.bottomRow()`
- per ogni `CardSummary` viene costruito un nodo grafico con `buildCardNode(...)`

Se una riga e' vuota:
- viene mostrato `buildEmptyState("No cards available.")`

7.8 Tessere offerta

Metodi:
- `rebuildOfferTiles()`
- `buildOfferTile(...)`

Logica:
- la tessera e' cliccabile solo se:
  - lo stato e' `ROUND_OFFER`
  - e' il turno del giocatore locale
  - la tessera e' disponibile

Se cliccabile:
- cursore `HAND`
- `setOnMouseClicked(...)`
- callback `onChooseOffer.accept(tile.index())`

Se la tessera e' occupata:
- viene disegnato sopra il totem del giocatore occupante

Ogni tessera ha anche un tooltip con:
- id tessera
- top picks
- bottom picks
- food gain
- disponibilita'

7.9 Ordine di turno

Metodi:
- `buildMinimalTurnOrderBar()`
- `currentTurnOrderSpaces()`
- `buildMinimalTurnOrderEntry(...)`
- `rebuildMinimalTurnBar()`

La board attuale usa una versione minimale dell'ordine di turno.

Comportamento:
- se `snapshot.turnOrder()` e' disponibile, usa quello
- se e' vuoto ma ci sono giocatori, costruisce un fallback dai player
- ogni entry mostra il nickname
- quella attiva viene evidenziata

Nota importante di manutenzione:
- nel file esiste anche `turnOrderTrackPane`
- esistono anche `buildTurnOrderRow(...)` e `buildMiniPlaceholder(...)`
- pero' nel codice attuale non sono usati dal layout finale
- `rebuildTurnOrder()` contiene esplicitamente un commento che indica che il vecchio track non e' piu' usato nella design attuale

Quindi:
- l'ordine di turno vero mostrato oggi e' la barra minimale
- il track piu' ricco e' codice legacy/residuo

7.10 Ranking finale

Metodo:
- `rebuildRanking()`

Quando compare:
- `snapshot.finished()`
- oppure stato `END_GAME`
- oppure stato `END_SCREEN`

Come viene costruito:
- copia `snapshot.players()`
- ordina per:
  - `prestigePoints` decrescente
  - `nickname` crescente
- costruisce una riga con:
  - posizione
  - totem
  - nickname
  - punti prestigio

7.11 Costruzione delle carte

Metodi:
- `buildCardNode(...)`
- `buildTooltipText(...)`
- `buildSurfaceArt(...)`

Come funziona:
- `buildCardNode(...)` chiede l'immagine al resolver
- se l'immagine esiste, crea un `ImageView`
- altrimenti crea un placeholder testuale

Tooltip delle carte:
- tipo
- era
- food cost se presente
- prestige se presente
- details

Click delle carte:
- permessi solo se `clickable == true`
- in quel caso la board chiama:
  - `onChooseCard.accept(cardSummary.selectionIndex(), topRow)`

7.12 Logica minima dei click

Metodo:
- `canPickCard(...)`

Permette il click solo se:
- esiste uno snapshot
- e' il turno del giocatore locale
- lo stato e' `ROUND_ACTIONS`
- la carta non e' evento
- restano picks nella riga corretta

Importante:
- questa non e' una validazione autorevole
- e' solo una protezione informativa lato view
- il controllo vero resta sul server

7.13 Totem

Metodo:
- `buildTotem(...)`

Funzione:
- prova a caricare il totem corretto dall'asset resolver
- se manca l'immagine, crea un fallback rotondo con iniziale del colore

7.14 Informazioni testuali della board

Metodi:
- `buildTurnLine(...)`
- `buildActionHint(...)`
- `formatEra(...)`

Questi metodi costruiscono il testo informativo che la board mostra all'utente:
- quanti giocatori mancano
- chi e' il giocatore attivo
- cosa si puo' fare in quella fase
- se il server sta risolvendo eventi automatici

7.15 Dati presenti nello snapshot ma non visualizzati nella board attuale

Questo e' un punto importante.

`PlayerSummary` contiene:
- food
- prestigePoints
- characterCount
- buildingCount
- `characterCards`
- `buildingCards`

Nel codice attuale della board:
- questi dati sono quasi del tutto inutilizzati
- il ranking usa `prestigePoints`
- la waiting room usa nickname e colore
- ma la schermata di gioco attuale non mostra il dettaglio delle carte possedute dai giocatori

Conferma tecnica:
- `buildCardNode(...)` ha ancora un ramo `ownedCard`
- pero' nel codice attuale nessuna parte della board costruisce davvero la sezione delle owned cards

Interpretazione:
- il backend prepara gia' i dati per visualizzarle
- la board attuale, pero', non sfrutta ancora quel supporto nel layout finale


8. `MesosGuiService`: come funziona
-----------------------------------

File:
- `src/main/java/it/polimi/ingsw/mesos/gui/MesosGuiService.java`

8.1 Ruolo

Fa da ponte fra GUI e rete.

Obiettivi:
- non bloccare il thread JavaFX
- incapsulare lo stato della sessione
- gestire subscribe/unsubscribe

8.2 Stato interno

Campi chiave:
- `stateLock`
- `ioExecutor`
- `client`
- `updateHandler`
- `currentGameName`
- `currentNickname`

8.3 Esecuzione asincrona

Metodo:
- `runAsync(...)`

Funzionamento:
- esegue l'azione su `ioExecutor`
- converte eccezioni in `CompletionException`

Thread pool:
- `Executors.newFixedThreadPool(4, new GuiThreadFactory())`

I thread creati:
- hanno nome `mesos-gui-io-N`
- sono daemon

8.4 Operazioni esposte alla GUI

- `connect(...)`
  - crea il `GameClient` corretto tramite `GameClientFactory`

- `fetchLobby()`
  - chiede la lobby

- `createAndJoinGame(...)`
  - crea la partita
  - poi fa join e subscribe

- `joinGame(...)`
  - join e subscribe

- `refreshSnapshot()`
  - chiede snapshot manuale

- `chooseOffer(...)`
  - invia scelta tessera

- `chooseCard(...)`
  - invia scelta carta

- `disconnect()`
  - chiude subscription e client

8.5 Join e subscribe

Metodo chiave:
- `joinAndSubscribeInternal(...)`

Ordine reale:
1. `joinGame`
2. salva `currentGameName`
3. salva `currentNickname`
4. fa `subscribe(...)`
5. se la subscribe va bene, restituisce uno snapshot
6. se la subscribe fallisce ma il join e' riuscito, restituisce failure con snapshot di fallback

Questo e' importante perche':
- la GUI puo' comunque mostrare uno stato anche se gli update live non partono

8.6 Chiusura del client

Metodo:
- `closeClientQuietly()`

Fa:
- se c'e' una partita attiva, tenta `unsubscribe(...)`
- poi chiude `client.close()`
- ignora le eccezioni IO in chiusura


9. `MesosAssetResolver`: come vengono trovate le immagini
---------------------------------------------------------

File:
- `src/main/java/it/polimi/ingsw/mesos/gui/MesosAssetResolver.java`

9.1 Ruolo

Risolve tutte le immagini usate dalla GUI e le mette in cache.

9.2 Cache

Campo:
- `imageCache`

Tipo:
- `ConcurrentHashMap<String, Optional<Image>>`

Questo evita di ricaricare sempre gli stessi PNG.

9.3 Carte

Metodo:
- `resolveCard(CardSummary cardSummary)`

Usa:
- `cardSummary.presentationId()`

Il resolver traduce il `presentationId` in un path reale del PNG.

9.4 Mapping tribe card

Regex:
- `^(hunter|builder|gatherer|artist|inventor|shaman)_era_([123])_([a-z])$`

Questo permette di mappare una carta tribu su:
- tipo
- era
- posizione interna del sottogruppo

9.5 Mapping building card

Regex:
- `^building_era_([123])_(\\d{2})$`

Permette di ricostruire il numero progressivo del PNG delle building.

9.6 Event card

Le event card non usano regex:
- hanno una mappa esplicita `EVENT_RESOURCE_PATHS`

9.7 Offer tiles B/C ed E/F

Dettaglio molto utile:
- B e C condividono la stessa immagine sorgente
- E e F condividono la stessa immagine sorgente

Come viene risolto:
- `loadOfferHalf(...)`
- carica l'immagine intera
- la taglia a meta'
- prende la meta' sinistra o destra a seconda del caso

9.8 Totem

Metodo:
- `resolveTotem(Color color)`

Mapping importante:
- `Color.BLACK -> /cards_png/totems/totem_purple.png`

Quindi nel gioco il colore logico `BLACK` viene rappresentato visivamente con il totem viola.

9.9 Altri asset

Metodi:
- `resolveHeroImage()`
- `resolveTribeBack(Era era)`
- `resolveBuildingBack(Era era)`
- `resolveRoundEventInfo()`
- `resolveEndGameInfo()`
- `resolveBackgroundImage(String filename)`

Nota:
- alcuni di questi asset sono oggi supportati ma non tutti sono usati nel layout finale corrente


10. `MesosUserMessageMapper`: pulizia dei messaggi
--------------------------------------------------

File:
- `src/main/java/it/polimi/ingsw/mesos/gui/MesosUserMessageMapper.java`

10.1 Ruolo

Serve a tradurre messaggi di backend e rete in testi piu' leggibili per la GUI.

10.2 Metodi principali

- `describeResult(...)`
- `describeUpdate(...)`

Conseguenza:

16. Cose da sapere per manutenzione futura
------------------------------------------

1. La GUI non usa FXML.
- Se vuoi aggiungere una schermata, oggi va costruita via codice JavaFX.

2. Il cuore del flusso e' `MesosClientApplication`.
- Se una schermata non si apre, spesso il problema e' li.

3. Il cuore del rendering partita e' `MesosGameBoardView`.
- Se la board si rompe visivamente, quasi sempre devi intervenire li o nel CSS.

4. Il cuore della rete GUI e' `MesosGuiService`.
- Se connect/join/refresh/update non vanno, guarda li.

5. Il server resta autorevole.
- Non mettere logica di regole nella view.

6. Gli snapshot sono il contratto vero fra backend e GUI.
- Se manca un dato nello snapshot, la GUI non puo' disegnarlo bene.

7. Alcune parti sono gia' predisposte ma non pienamente usate.
- In particolare le carte possedute dai giocatori sono esportate dal backend ma non mostrate nel layout finale attuale della board.

8. Ci sono residui legacy nel codice.
- Metodi come `buildHeroCard`, `buildDeckDock`, `buildTurnOrderRow`, `buildMiniPlaceholder`
  o strutture come `turnOrderTrackPane` fanno capire che la GUI e' passata attraverso piu' iterazioni.
- Anche alcune callback gia' previste nella board, come `onRefresh` e `onDisconnect`, oggi esistono ma non sono esposte dal layout finale della schermata di gioco.
- Prima di cancellarli, conviene verificare se vuoi recuperarli o se vuoi davvero semplificare.


17. Riassunto finale molto diretto
----------------------------------

La GUI attuale di MESOS e':
- un client JavaFX puro
- costruito interamente via codice
- senza FXML
- con una schermata connessione
- una lobby
- una waiting room
- una board di gioco live
- una classifica finale incorporata nella board

Il launcher client:
- avvia JavaFX tramite `MesosClientLauncher`
- delega il lavoro vero a `MesosClientApplication`

JavaFX viene usato per:
- costruire tutta l'interfaccia
- gestire scena e finestra
- applicare stile CSS
- mostrare immagini
- mostrare tabella lobby
- gestire overlay e alert
- aggiornare la GUI in sicurezza con `Platform.runLater(...)`

Il backend supporta la GUI:
- fornendo snapshot completi
- fornendo `presentationId` per le immagini
- fornendo dati di lobby, partita, ordine di turno, offerte e giocatori

La regola architetturale piu' importante e':
- la GUI visualizza
- il service comunica
- il server decide
